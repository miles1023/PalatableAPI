## Part 1 — CI/CD Runner Setup

### Runner Chosen: `ubuntu-latest` (GitHub-hosted)

**Why Ubuntu?**

This repository is a research and documentation repository. It contains YAML data files,
Markdown documents, and a Python validation script. There is no game engine build, no
Windows-specific toolchain dependency (UE4SS, Cheat Engine, x64dbg live on the developer
machine, not in CI), and no compilation step. Ubuntu is the correct default for this kind
of project for the following reasons:

| Criterion | Ubuntu | Windows | macOS |
|-----------|--------|---------|-------|
| Cost (public repo) | Free, unlimited | Free, but slower | Free, but slowest |
| Startup time | Fastest (~10–15s) | ~40–60s | ~60–90s |
| Linting toolchain | Full native support | Works, no advantage | Works, no advantage |
| Python availability | Pre-installed | Pre-installed | Pre-installed |
| Node.js availability | Pre-installed | Pre-installed | Pre-installed |
| Game tool dependency in CI | None (tools are local) | None | None |

**When to add a Windows runner:**

A dedicated `windows-latest` job should be added when any of the following become true:

- A Python build script produces a `.dll`, `.exe`, or `.pak` artifact for distribution
- AOB signature generation is automated and needs to attach CE/Ghidra in CI
- The Steam Workshop uploader CLI is integrated into the release pipeline

None of those conditions exist today. Keep `ubuntu-latest` until they do.

### Workflows Implemented

#### `.github/workflows/ci.yml`

Three jobs run on every push and pull request targeting `main`:

| Job | Tool | What it checks |
|-----|------|----------------|
| `lint-yaml` | `yamllint` | Syntax and style of all `.yml` files in `evidence/`, `findings/`, `schemas/`, and `survey/` |
| `lint-markdown` | `markdownlint-cli` | Syntax of all `.md` files (UE4SS context reference files excluded) |
| `validate-schema` | Custom Python script | Every canonical finding file (Markdown with YAML front matter) contains all required fields from `schemas/FINDING_SCHEMA.md` |

**Security notes:**

- Workflows use pinned major versions (`actions/checkout@v4`, `actions/setup-python@v5`,
  `actions/setup-node@v4`) following GitHub's recommended practice.
- No secrets are required or used. The workflow is entirely read-only against repository
  content.
- `concurrency` is set to cancel in-progress runs on rapid pushes, avoiding redundant runs.

## Part 2 — Chain-of-Thought Logic Review

Every file in the repository was examined. Findings are grouped by category.

### 2.1 — Organizational Structure: Coherent

The folder layout defined in `CLAUDE.md` and `RULES.md` is internally consistent.

- `survey/` contains phase-0 scope outputs (`SURFACES.md`, `GAME_SYSTEMS.md`).
- `intake/` serves as the raw/processed landing area; the rule "never edit raw files" is
  sound and well-stated.
- `findings/`, `systems/`, `memory/`, `hooks/` form a clear promotion hierarchy.
- `schemas/FINDING_SCHEMA.md` defines the contract. `workflow/PIPELINE.md` defines the
  process. Both are complete and cross-reference each other.
- `evidence/sources-2026.md` is correctly scoped to verified 2026 sources only.

**No issues found.** The structure is well-organized for an RE capture project.

### 2.2 — Schema and Pipeline Alignment: Good, One Gap

The `FINDING_SCHEMA.md` requires the following fields: `type`, `name`, `description`,
`game_system`, `surface`, `source.tool`, `source.session`, `source.detail`, `confidence`,
`status`.

The two canonical finding files already in the repository
(`memory/structs/FFixedPoint-layout.md`, `memory/structs/FFixedPoint64-layout.md`) were
validated by the new CI script and pass. Both are correctly formatted.

**Gap identified:** The `PIPELINE.md` at Step 10 says to "update the relevant
`systems/<name>/README.md` to reference the new finding," but there is no corresponding
entry in `systems/player-character/README.md` or `systems/pal-character/README.md`
pointing to the FFixedPoint layout findings. This is minor — the pipeline step is
advisory, not enforced — but is worth noting for future sessions.

### 2.3 — Confidence Rules: Well-Defined and Consistently Applied

The three-tier confidence system (`confirmed`, `inferred`, `speculated`) is defined in
both `RULES.md` and `schemas/FINDING_SCHEMA.md` with identical definitions. The
pre-migration YAML files use this system correctly: data sourced from community
documentation is marked `inferred`, not `confirmed`. This is honest and safe.

The note "Confirming an inferred finding is straightforward. Correcting a wrongly-confirmed
finding wastes time" is a sound operating principle.

**No issues found.**

### 2.4 — Training Data Warning: Correctly Enforced

`CLAUDE.md` is clear that Palworld training data is ~2 years out of date and must never
be used as a reliable source. All 21 game-system entries in `survey/GAME_SYSTEMS.md` are
tagged `[UNVERIFIED — training data]`. Two surface entries have been corrected via live
evidence (`Steam Workshop: CONFIRMED LIVE`, `RCON: DEPRECATED`).

The memory for this fact exists and has been maintained correctly.

**No issues found.**

### 2.5 — Version Tracking: Correct

`evidence/game-versions.yml` tracks versions 0.7.1, 0.7.3, and 1.0 (upcoming). The
SHA-256 hash discrepancy between the community Mappings.usmap and the live-generated
DumpUSMAP output is correctly documented with a warning. This is good practice.

`CLAUDE.md` and `RULES.md` both document the same current version (0.7.1 at time of
writing RULES.md, 0.7.3 in CLAUDE.md). The discrepancy is benign — CLAUDE.md was updated
more recently — but a single authoritative version reference in `evidence/game-versions.yml`
is the correct approach and is already in place.

**No issues found.**

### 2.6 — Pre-Migration Data: Correctly Quarantined

`findings/pre-migration/` contains the old-format data. Both `RULES.md` and `PIPELINE.md`
explicitly state that this data should be treated as Step 2 raw input and must not be
assumed correct without live verification. The confidence level on pre-migration entries
accurately reflects community research, not live confirmation.

**No issues found.**

### 2.7 — Out-of-Scope Guardrails: Clear and Consistently Stated

`CLAUDE.md`, `RULES.md`, and `schemas/FINDING_SCHEMA.md` all explicitly prohibit API
design work, backend implementation, and SDK tooling until the RE map is complete.
`future-api/` is intentionally empty. The "what is out of scope" section is repeated in
multiple files, which is intentional redundancy to prevent scope creep.

**No issues found.**

### 2.8 — Minor Inconsistency: Game Version in CLAUDE.md vs RULES.md

`RULES.md` (last updated 2026-05-15) states current version 0.7.1.
`CLAUDE.md` (last updated 2026-05-16) states current version 0.7.1 in the header but
notes that 0.7.3 is the current roadmap target in the `evidence/game-versions.yml` context.
The authoritative source is `evidence/game-versions.yml` (which correctly shows 0.7.3 as
the current partially-verified install).

**Recommendation:** Update the "Game Version" section of `RULES.md` to reference 0.7.3 as
the current working version, consistent with `evidence/game-versions.yml`. This avoids
confusion at the start of future sessions.

## Part 3 — Roadmap Smell Test

### 3.1 — Overall Assessment: Coherent and Well-Structured

The roadmap in `ROADMAP.md` is a detailed, 750+ line document covering 6 phases across
22 weeks. The vision (a BakkesMod-style framework for Palworld) is clearly articulated,
technically sound, and grounded in verified sources. The risk matrix is honest and
actionable.

No fundamental smell issues were found. The following notes are refinements.

### 3.2 — Phase 1 and Phase 2 Overlap with Current RE Work

The ROADMAP.md defines Phase 1 as "Environment & Foundation" and Phase 2 as "Game Mapping
& Recon." The current repository state (as documented in `CLAUDE.md`) is already deep into
Phase 2 equivalent work: scaffolding is complete, 21 game systems are documented,
14 surfaces are mapped, and 13 verified 2026 sources are recorded in `evidence/`.

**Finding:** The ROADMAP.md treats the RE scaffolding as a future activity, but the
repository has already completed most Phase 0–2 groundwork. The roadmap should acknowledge
this. Phases 1 and 2 are partially complete.

**Recommendation:** Add a "Current State vs. Roadmap" section to ROADMAP.md that maps
what has been done in the current repository to the Phase 1 and Phase 2 gates. This makes
it easier to communicate progress and identify what actually remains.

### 3.3 — AOB Signature Strategy: Correct but Needs a CI Hook

Phase 5.2 describes AOB-based address resolution as "the single most important technical
differentiator vs PalSchema." The strategy is sound. However:

- AOB signatures are stored in a `/signatures` directory (referenced in Phase 2.8), but
  this directory does not yet exist in the repository.
- The update pipeline (Phase 6.5) describes a manual process of launching Palworld and
  re-scanning via CE MCP. There is no CI job for this because it requires a local Windows
  machine with the game running.

**This is not a smell — it is an inherent constraint.** AOB validation cannot run in
GitHub-hosted CI. However, the repository should document this explicitly so future
contributors understand why there is no automated signature-validation CI job.

**Recommendation:** Create `signatures/README.md` that explains the AOB signature format,
how to update them after a Palworld patch, and why CI cannot automate this step.

### 3.4 — Linux Server Support Risk: Correctly Identified but Under-Mitigated

The risk matrix notes "Linux dedicated server support never stabilizes for UE4SS — Medium
likelihood, Medium impact." The mitigation is "Document Windows-only for UE4SS mods. .pak
mods work cross-platform."

This mitigation is pragmatic but leaves a gap: server operators running Linux containers
(the dominant production hosting model in 2026) cannot use UE4SS-dependent features of
the framework. This is a significant adoption barrier for the dedicated server community.

**Recommendation:** Add an explicit Phase 4 or Phase 5 item to document which framework
modules are Linux-compatible (DataTable-based features using PalSchema, REST API
integration) and which are Windows-only (UE4SS hooks, memory modification). Modders
should be able to detect this at plugin load time via the framework's graceful degradation
system.

### 3.5 — Palworld 1.0 "Top Secret" Risk: Well-Handled

The roadmap explicitly acknowledges that Palworld 1.0 internals are labeled "Top Secret"
with no advance patch notes. The AOB scanning strategy and graceful degradation design
directly address this. The 48-hour 1.0 compatibility beta target is realistic given the
MCP-accelerated RE pipeline.

**No smell here.** This is the most technically mature part of the roadmap.

### 3.6 — Project Name Gap: Actionable

The roadmap lists five name candidates (PalAPI, PalForge, PalKit, PalFrame, OpenPal) and
states "owner picks." As of this review, the repository is named `PalatableAPI`, which
does not appear in the candidate list.

**Recommendation:** Either confirm `PalatableAPI` as the chosen name and update the
roadmap accordingly, or finalize a name from the candidate list before beginning Phase 3
(when public-facing workshop items will be created and a name change becomes costly).

### 3.7 — Phase 3 Gate: Strong

The Phase 3 gate ("No Phase 4 work until ALL Phase 3 tests pass on v0.7.3") is the right
approach. Enforcing this gate in CI (once tests exist) would strengthen it further. The
test runner design (scripts callable from UE4SS console) is practical.

### 3.8 — Documentation Generation (Phase 5.6): Plan is Sound

Auto-generated documentation from API source code, hosted on GitHub Pages, is a standard
best practice. The workflow for this should be a separate GitHub Actions workflow that
triggers on release tags. This does not need to be implemented now but should be
scaffolded in Phase 5.

### 3.9 — Timeline Feasibility: Aggressive but Plausible

The 22-week timeline targeting Palworld 1.0 (Q4 2026) is aggressive given that:

- All coding is AI-generated (stated in ROADMAP.md)
- The RE work (Phase 2) requires live game sessions with MCP-bridged tools
- Phase 4 covers 14 API modules in 7 weeks

The contingency plan (Tier 1 modules first, remaining modules as post-launch updates) is
the right way to manage this. The critical path is:
`RE completion → Core API → Test suite → AOB resilience → Release`

**Recommendation:** Define Tier 1 (Pals, Player, Items, Base, Combat) as the minimum
viable release target and explicitly scope Phase 4 to ship Tier 1 by Sep 14 regardless
of Tier 2/3 status. This is already implied by the roadmap but should be made explicit.
